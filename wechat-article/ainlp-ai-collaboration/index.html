如何与 AI 协作，让每次工作都产生复利

Eugene Yan 在这篇文章中梳理了自己与 AI 协作的方法：每次完成的工作、每次纠正，都应该让下一次协作更省力。他把这个想法落实到了目录、CLAUDE.md、Skills、验证和反馈中，以下是全文翻译。

怎样才能高效地与 AI 一起工作？工作流应该是什么样，怎样扩大规模，又怎样让整套系统不断改进？最好，这一切还能产生复利。每一份完成的成果——代码、文档、分析、决策——都成为下一次会话的上下文；每一次纠正，都更新配置，减少今后的错误。我仍在摸索，不过这些问题已经回答过太多次，索性写下来，下次再有人问，就可以直接发链接了。

如果你经常使用 AI，大概已经在采用其中不少做法。不过，我相信背后的原则有很广的适用性：提供好的上下文，把自己的偏好写进配置，让验证变得容易，把更大的任务交出去，再把反馈接回来。如果某个做法不适合你，就调整它背后的原则，发明自己的方法。读的时候也可以留意：这些其实都不是 AI 独有的事，而是你带一位新同事入门、与他一起工作的方式。

把上下文当作基础设施

帮助模型在你的上下文中找到路。比如，我把所有代码放在 ~/src，把所有知识工作放在 ~/vault，后者再按 projects/、notes/、kb/ 等目录组织。工作整理得有条理，模型就更容易用 grep 或 glob 检索上下文。目录树清楚了，它也更容易找到已有代码、项目文档和分析，借助这些积累改进当前的工作。

让模型接入组织的上下文。组织知识很可能散落在 Slack、Drive、邮件等地方，模型也能从中受益。这些工具大多提供了可供 Claude Code、Cowork 和 Claude.ai 使用的 MCP。除此之外，我还会为每个项目维护一份 INDEX.md。它是一份带注释的索引，列出相关文档和频道；每一项都有 URL、负责人，以及一小段介绍，说明里面有什么、什么时候该读。注释很有帮助。光列 URL，模型就得逐个打开，才能判断哪些相关，既花时间，也占上下文。提前写好注释，就是把这份费力的工作做一次，再存进索引。

把每次新会话都当成新同事入职。每次开启新会话，模型都从一张白纸开始。因此，可以把每个项目的 CLAUDE.md 当作新同事第一天会收到的入职文档。Claude 扫描过我各个项目的 CLAUDE.md，发现其中有缩写、项目代号的词汇表，也有用来区分同名同事的说明。我还会在 CLAUDE.md 里建议阅读顺序，比如先浏览 INDEX.md，再看待办清单，最后读具体主题的笔记。

建立自己的记忆层。默认情况下，模型不会记住上次会话发生了什么，值得保留的内容都应该写到磁盘上。我把记忆层分成两部分：~/vault 保存项目状态、工作成果和领域知识等事实；~/.claude 及其中的 CLAUDE.md、skills/、guides/ 则保存我的偏好、工作流和个人品味。前者提供上下文，后者提供配置。

把品味写进配置

先从 ~/.claude/CLAUDE.md 开始。Claude 会在每次会话启动时读取它，我把它当作一份行为约定。我的 CLAUDE.md 会写明这些偏好：表达要多直接、什么时候该提出异议、怎样处理错误、应该教我什么，等等。下面是删节版：

<behavior>
- Be direct and push back when you disagree; if my approach has problems, say so.
- When unsure about something, say you're unsure rather than guessing confidently.
- When something fails, investigate the root cause before retrying.
- Keep diffs scoped to the task: no drive-by reformats or unrelated refactors.
...
</behavior>

<teaching>
I'm always picking up new systems and domains. When a key term surfaces that I
likely haven't internalized, explain it in 1-2 sentences and then move on. Format:

> 💡 followed by 1 - 2 sentence explanation
...
</teaching>

按目录划分范围：全局、仓库、项目。处处适用的偏好，比如行为、长期目标、教学方式，放进 ~/.claude/CLAUDE.md。某个仓库的约定，比如 lint、命名和拉取请求规范，放在仓库根目录。项目专属的上下文，比如目录布局和领域知识，放在项目目录。在子目录里启动 Claude Code 时，它会向上遍历目录树，加载沿途的每份 CLAUDE.md。会话进行中，模型进入某个子目录时，也会读取那里的 CLAUDE.md。更多细节可查阅文档。

CLAUDE.md 太长时，就拆开。过长的 CLAUDE.md 会变成上下文负担：无论当前会话需不需要，每次都会加载全部内容。解决办法是把部分内容拆成按需加载的指南。不要用 @import，那只是把内容内联进来；应当在 CLAUDE.md 中告诉模型，相关时再去读取。这样，正在构建评估的会话就可以跳过文档写作指南。下面是一段指南索引的例子：

<guides>
- Docs, 1-pagers, any writing: ~/.claude/guides/writing.md
- Eval building and reports: ~/.claude/guides/evals.md
- Dashboards: ~/.claude/guides/dashboards.md
...
</guides>

如果一件事每周至少做一次，就把它做成 Skill。Skill 是一份包含名称、触发条件和操作流程的 Markdown 文件，由模型按需加载。可以把它理解为写在 Markdown 里的工作流，其中也能包含判断逻辑。例如，我的 /polish Skill 会查看成果的差异：如果产出指标，就运行相应评估；如果输出会在浏览器中呈现，就通过 Claude in Chrome 检查；如果两者都不是，就运行代码，读取输出或错误。Skill 不只记录步骤，也记录哪些步骤适用。我的几个 Skill 包括：

  • /polish
    ：检查 bug，简化代码，验证输出（通过评估、Claude in Chrome 或其他方式），迭代到没有关键反馈，再起草 PR。
  • /write
    ：通过访谈帮我形成提纲，启动研究子 Agent，写初稿，再用对抗式批评给出反馈，迭代到没有关键反馈。
  • /daily
    ：读取我的日历、Slack、PR、昨天的日志等，写出今天的优先事项。

我通常把 SKILL.md 保持得短小，聚焦工作流和分派。模板、脚本等知识另放在独立文件里，模型需要时才读取或运行，就像按需加载的指南一样。

先做一遍任务，再请模型把它变成 Skill。我大多数 Skill 都是这样建立的：先在普通会话里交互完成一次任务，再让模型把刚才的过程整理成 Skill。接着，用它执行相同或类似的任务。输出难免需要纠正，我会在同一个会话里改，让反馈留在会话记录中。最后，请模型根据这些纠正和反馈更新 Skill。你也可以拿理想输出的例子作为起点，让模型提取模式，比如代码如何组织，或文档的结构与语气。

通过会话记录改进 Skill，而不是直接改文件。第一版 Skill 很少能完美运行，因为它容易过度贴合最初那次会话。这很正常。运行后需要修改输出时，就在会话里纠正，尽量不要直接打开 SKILL.md 编辑。在会话中反馈，会让模型得到前后对照：我们做了什么，我想要什么，以及为什么。这些对照会不断积累在会话记录里。等输出正确了，再让模型把反馈合并进 Skill。几轮之后，Skill 会逐渐稳定下来，最终输出也几乎不需要你再改。

不过，并不是每个任务都需要这些上下文。头脑风暴、探索和写粗稿时，我喜欢用简单模式（CLAUDE_CODE_SIMPLE=1 claude）。这种模式仍会加载 CLAUDE.md，但不会加载 Agent 运行框架中的 hooks、skills 和大量使用工具的循环。它让我更直接地接触模型；当我只是想边说边思考，而不是交付成果时，这正是我需要的。

用验证换取自主性

把验证前移，在写入时就发现错误。我把验证看作一架梯子：底部便宜且确定，顶部昂贵，而且需要判断。我们要尽量在较低的阶梯解决问题。靠近底部的是编辑后触发的 hooks，会对模型刚更新的文件运行 ruff format、ruff check --fix。这套过程是确定性的，也不消耗 token。再往上，才是测试、评估、LLM 审查等。

让模型方便地验证工作。给它反馈闭环，让它能够改进输出。如果系统会产出指标，就让模型运行评估并优化；如果输出会在浏览器中呈现，就让模型通过 Claude in Chrome 检查；如果都不是，就让它运行程序、读取错误。例如，构建 Docker 镜像时，我让模型执行构建、读取错误、修改 Dockerfile，再重新构建。调整 harness 时，模型运行评估、阅读会话记录、修复失败。做仪表盘时，模型会在 Chrome 中检查提示框是否正常显示、标签是否重叠，以及叙述是否与数字相符。

对于长时间运行的任务，让模型观察模型。长会话中的错误会不断累积，方向也可能逐渐偏移。一个办法是开启第二个具有全新上下文的会话，让它阅读原始需求和主会话最近几轮的记录。我的最简配置使用两个 tmux 窗格，一个负责主要开发，另一个充当结对程序员。初始指令和后续提示会追加到一份共享文件中。结对程序员会定期启动，对照需求检查主会话最近的记录；发现不对，就给出反馈，帮助纠偏。

具体可以有不同的检查方式。比如，结对程序员可以关注执行偏移：模型有没有把任务做对？这是局部、战术层面的问题，例如忽略错误、报告错误指标，或者偏离需求。另一类是方向偏移：模型做的是不是正确的任务？这属于更宏观、战略层面的问题，比如误解最初意图，花了几个小时搭出一个错误的东西。执行偏移要经常检查，方向偏移则偶尔检查。

通过委派扩大规模

把越来越大的工作单元交出去。有时，我们与模型结对编程：任务短、反馈快，人始终参与。这适合快速迭代、探索性分析和原型开发。但模型越来越强，我们也应该尝试委派更大的任务。先讲清意图、约束和成功标准，再让模型工作。无法验证的工作也就无法放心委派，因此首先要定义成功标准和指标。我们要从一次给一条指令，转向把计划讲充分，再让模型端到端地执行：

“针对这些评估套件，给每个套件构建独立容器，先做冒烟测试，确认都能构建。然后完整运行，记录评估指标和会话记录，再让子 Agent 阅读记录，确认评估执行正确。每项评估运行 n 次，以计算置信区间。最后生成报告，检查是否符合报告指南，再通过 Slack 把结果和报告 URL 发给我。”

并行运行会话，找到瓶颈。委派更大的任务，意味着可以同时推进更多工作。Claude 说，我通常同时运行三到六个会话。瓶颈已经从亲手干活，转向写出清楚的需求，并足够快地检查输出，让整条流水线持续运转——中间那段执行工作正在被抽空。如果并行会话共用一个仓库，就使用 git worktrees，让每个会话各有一份检出目录，不会覆盖彼此的改动。

让会话状态容易观察。同时运行多个会话时，我需要知道每个会话的状态，哪个需要关注。在我的 Mac 上，会话结束时，stop hook 会播放声音，例子见下方。tmux 窗口标题使用状态表情（⏳ 工作中；🟢 已完成），再配上一段由 Haiku 生成的简短标签，让我知道各个窗格在做什么。Claude Code 状态栏则显示上下文用量和当前模式。这样，stop hook 的声音告诉我任务完成了，tmux 标题告诉我是哪个任务，状态栏再提供细节。

# Example stop hook alert
"Stop": [
    {
    "hooks": [
        {
        "type": "command",
        "command": "if command -v afplay >/dev/null 2>&1; then afplay -v 1.0 /System/Library/Sounds/Glass.aiff; else tput bel; fi"
        }
    ]
}

不在电脑前也能查看进展。Claude Code 的 /remote-control 让这件事很方便。通勤或排队时，我会打开 Claude 应用的 code 标签页，看看哪些任务在运行、哪些卡住了；必要时，补充上下文或新指令，让停滞的会话继续推进，避免闲置几个小时。不过，只在确有急事时这么做；想专注眼前的人和事，或出去走走时，就别这样了。

把反馈接回来

公开协作，让上下文保持充实。在共享文档、仓库和频道中工作，每个人——包括模型——都更容易检索和利用上下文。今天分享的东西，就是明天组织上下文的一部分。不妨做个简单测试：一位新同事能不能仅凭共享上下文，复现你上周的工作？如果能，说明你为组织上下文做出了不错的贡献；如果不能，宝贵的上下文就还困在你脑子里。我会在 CLAUDE.md 中写下指令，让模型每完成一项比较大的任务，就到工作日志频道发一条简短更新，附上成果 PR 或文档的链接，以此自动化一部分工作。

从会话记录里挖掘配置的改进机会。让模型阅读过去的会话记录，寻找缺口。我扫描过自己大约 2,500 条用户发言，其中相当一部分出现过“你能不能再……”“你检查过……吗”“还是不对”等表达。这说明，有些事情模型本该主动完成，我应该更新 CLAUDE.md 或 Skill；也可能是缺少某个验证步骤，或者那个步骤坏了。出现次数能说明同一种纠正有多频繁，会话记录则展示究竟哪里出了问题。这也是我总在会话里纠正的原因：记录可以成为下一次更新 CLAUDE.md 或 Skills 的输入。

定期重构和删减。配置越积越多，就可能重叠或冲突。模型忽略一条规则，有时是因为另一条规则与它矛盾。解决办法是定期整理。每条规则或偏好都应该只在一个地方维护，关键指令可以在主 CLAUDE.md 中重复。我也会检查散落在目录里的 settings.json，把它们合并回 ~/.claude。

随着模型进步，具体配置很可能改变，但我认为这些原则仍然适用：提供好的上下文，把品味写进配置，降低验证成本，委派更多工作，再把反馈接回来。我们做的事，就是通过一次次反馈，培养一位协作者。想想看，这些原则也同样适用于人与团队的协作。

想开始的话，可以让模型读取这份 SETUP.txt，帮你应用其中的做法。我也很想知道哪些实践或原则对你有用，欢迎在下面留言，或联系我！

补充一句：这不仅关乎个人工具，也关乎怎样设计 Agent harness、建立团队规范，以及搭建组织基础设施。不妨带着这几个层面，再读一遍。
